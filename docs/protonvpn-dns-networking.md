# ProtonVPN flips break all networking (ENOENT / API errors)

Companion to [protonvpn-debian.md](protonvpn-debian.md) (which covers why
`protonvpn connect` fails on headless Debian). This doc covers a *separate*
problem: a ProtonVPN up/down **flip** leaving the whole box unreachable —
every DNS lookup fails with `ENOENT` and every outbound connection dies —
until reboot. On the affected machines this manifested as Claude Code (and
anything else hitting the network) failing with `API Error` / `ENOENT` across
**every** session at once.

Hit on **dimitris-a** and **dimitris-b** (Debian 13, ProtonVPN CLI 1.0.1).

## Two independent failure modes

Both are triggered by a Proton flip. Either one alone bricks connectivity.

### 1. DNS left empty — the one that actually bit us

The primary uplink (`enp0s31f6`) is **unmanaged by NetworkManager** and there
is **no systemd-resolved**. NetworkManager owns `/etc/resolv.conf`. When Proton
connects it sets DNS via NM; when it tears down, NM has no baseline connection
to restore DNS from, so it regenerates `/etc/resolv.conf` containing only:

```
# Generated by NetworkManager
```

…with **no `nameserver` line at all**. Every lookup then fails with `ENOENT`.
This is exactly what happened on dimitris-b — routing was completely fine, DNS
was simply gone.

### 2. Kill-switch route hijack — the theoretical one

Proton's NM kill switch creates a dummy interface `pvpnksintrf0` with a
**metric-98 default route**, plus `pvpn-killswitch*` / wireguard NM connections.
If the CLI is interrupted (timeout, async race, signal, keyring failure — and it
*is* currently always interrupted, see the keyring issue in the companion doc)
these orphan: the dummy hijacks the default route and blackholes traffic. Symptom
here is "no route" / connection-refused rather than DNS errors.

## The fix

### DNS pin (permanent, run once per machine)

`scripts/packages/vpn-dns-pin.sh` — run once with sudo:

```bash
sudo bash ~/dotfiles-debian/scripts/packages/vpn-dns-pin.sh
```

It:
1. writes `/etc/NetworkManager/conf.d/90-dns-none.conf` → `[main]\ndns=none`
   (NM never touches resolv.conf again),
2. writes a static `/etc/resolv.conf` (`1.1.1.1` / `8.8.8.8`),
3. reloads NetworkManager,
4. sets the **immutable bit** (`chattr +i`) so *nothing* can rewrite it.

Survives reboots and VPN flips. One-time, permanent. Revert with `--revert`.

**Trade-off:** while Proton is up, DNS queries go to 1.1.1.1/8.8.8.8 *through the
tunnel* — Cloudflare/Google see the Proton exit IP, not you, so it is **not** an
ISP-visible DNS leak. Proton's own resolver just isn't used. Acceptable.

### vpn-cleanup (backup, for the route-hijack mode)

`scripts-local/.local/bin/vpn-cleanup` was hardened to also:
- dynamically delete **all** pvpn/proton/wireguard NM connections (not just a
  fixed name list),
- remove leftover `pvpn*` interfaces,
- restore DNS if it's writable and broken,
- verify `getent hosts api.anthropic.com` before exiting.

Runs via polkit — **no sudo needed**. Run it if a flip ever leaves stale routes.

## Recovery cheat-sheet

| Symptom after a Proton flip | Fix |
|---|---|
| `ENOENT` / "could not resolve host" | DNS pin already prevents this; if unpinned: `sudo bash vpn-dns-pin.sh` |
| "no route" / connection refused, routes look wrong | `vpn-cleanup` (no sudo) |
| Not sure | `vpn-cleanup` first, then check `cat /etc/resolv.conf` |

## Gotcha for future debugging

`ssh t-dmi-b` = **dimitris-b** (100.122.156.78). A Claude Code / shell session
may be running on **dimitris-a** while the broken box is dimitris-b — always
`hostname` first so you fix the right machine.
